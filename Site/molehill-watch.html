The problem

Most SQL Servers are fine right up until they are not.

Backups that have been failing quietly for a month. A CHECKDB nobody has run since the server was built. An Availability Group that would not actually fail over. Disks filling up at a predictable rate that nobody is watching.

None of this needs a full-time DBA. It needs somebody competent looking at the right things every week, and being available when something does go wrong.

That is all Molehill Watch is. A monitoring pack that runs on your servers, and our DBAs reading what it finds.

Questions people ask

Before you send this to your infrastructure team.

Does anything leave our network?

No. The collectors write to a database on your own server. The weekly report is built there too. It only leaves if you configure Database Mail to send it - and even then query text is excluded from the e-mail by default. If you would rather nothing was e-mailed at all, reports can be exported to files and picked up from your jump box.

What does it do to server performance?

The collectors are lightweight and run a few times a day as SQL Agent jobs, reading from dynamic management views and system tables rather than running heavy queries. They keep a rolling history in their own schema so the weekly report is a read of data already collected, not a scan of your databases.

What access do you need?

Sysadmin to install (it creates jobs and reads server-level state), then an account that can read health, job and performance data day to day. Remote access to each covered server via your VPN, Azure Bastion or an agreed equivalent, and SSMS or similar on a jump box. It is all written down in the onboarding checklist.

Can it go in our existing DBA database?

Yes. Everything is created in an mw schema, so it never clashes with objects you already have, and the uninstall script removes only that schema and its four Agent jobs. Nothing else on the instance is touched.

We are on Azure SQL - does this still apply?

Azure SQL Managed Instance is covered like any other instance. Azure SQL Database does not have SQL Agent or server-level access, so it gets a read-only weekly report run from your jump box instead, covering the same ground the platform exposes: sizing, storage, index and query health, and failed connections.

What happens when something breaks at 2am?

Out-of-hours work is charged at the out-of-hours rate and is arranged rather than guaranteed - there is no 24/7 on-call built into the standard package. If you need overnight cover for a migration or a month-end, we agree it in writing beforehand.

What if we want to stop?

Three month initial term, then a month's notice ending at the close of a billing cycle. Run the uninstall script and the monitoring is gone. The collected history is yours - we will export it for you before it goes.
